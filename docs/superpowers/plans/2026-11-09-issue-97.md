# Win agent: /hack-coord event coordinator mode Implementation Plan (issue #97)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** `/hack-coord <event-slug>` starts (or takes over) one event coordinator that runs LAND's loop: issue, brief, build thread, separate reviewer per PR, merge, `COORD.md` line, handoff block near 140k, plus councils and a fresh-eyes review. All per-event output goes to the gitignored `hackathons/events/<slug>/`.

**Architecture:** One prose skill (`hackathons/agent/skills/hack-coord/SKILL.md`) and five committed templates in `hackathons/agent/templates/coord/`. No script and no install change: `install.sh` from #91 already links every folder in `hackathons/agent/skills/`. The skill finds the event folder the way `/hack-prep` does (realpath of its own base dir), launches threads with the T3 CLI (`t3 thread start`), and build threads report back with `t3 thread send`.

**Tech Stack:** Markdown skill for Claude Code, the T3 CLI (`$T3CODE_CLI_PATH`, which is `~/.t3/bin/t3`), `gh`, git. No new dependency.

**Spec:** issue #97 (`gh issue view 97`) and `~/Developer/docs/superpowers/specs/2026-11-09-hackathon-win-agent-design.md` (the "Coordinator mode" line). Sources, read only: `tools/status/README.md`, `tools/status/COORD.md`, `tools/status/HANDOFF-coordinator.md`, `tools/status/fresh-eyes-report.md`, `tools/status/briefs/`.

- No commit or push without the owner (this ticket's build). The plan's own commit steps are the owner-approved ones at gate 2.
- Leave `tools/status/` exactly as it is. Read it; do not move, edit or delete any file in it.
- Public repo. Nothing from `hackathons/events/` and nothing from LAND's logs is quoted in a committed file. Templates and the skill describe the structure in new words. - No HQ router template, no router role. The owner talks to the coordinator directly.
- Thread status file format is LAND's, unchanged: the five fields `name`, `issue`, `state`, `note`, `updated` from `tools/status/README.md`, "Thread status files". The templates quote the field rules from that README; that README is not per-event material.

Commit format falls back to `type(scope): summary (refs #97)` with the session's `Co-Authored-By` trailer, as #91 did. The final check (Task 4) is built from the ticket's **Done when** list.

## Decisions for gate 1 (the owner can change any)

- **D1. How threads start.** The coordinator launches every thread with the T3 CLI: `"${T3CODE_CLI_PATH:-$HOME/.t3/bin/t3}" thread start <event repo path> - --title "<title>" --worktree <base> --branch issue-<N>-<short>` with the one-line message on stdin, and `--json` to read the new thread id. Threads report with `t3 thread send <coordinator id> "<msg>"`. The coordinator's own id is `$T3CODE_THREAD_ID`. LAND used the MCP tools `t3_thread_launch` and `t3_thread_send` instead. Pick: the CLI, because it is one path that works from Bash in any T3 session, and the build can prove it. Without T3 (no CLI or no server), `/hack-coord` stops and says it needs T3 running.
- **D2. Where the event-only rules live.** On first start the coordinator asks the owner for the slot values in one question round and writes them, with the generic block, to `hackathons/events/<slug>/briefs/rules-common.md`. Every brief pastes that block in full, as LAND did. Slots: event repo (GitHub slug and main checkout path), base branch, teammates and what they own, ports never to use, product wording rules, council judges, merge rule (who merges, method, push rule, commit trailer rule), test commands. The last three are beyond the ticket's list: the merge rule is named in the ticket's Constraints, and test commands and base branch were in every LAND brief.
- **D3. Handoff.** Near about 140k the coordinator prepends a block to `HANDOFF-coordinator.md`, launches the next coordinator with `t3 thread start <event repo path> "/hack-coord <slug>"` (no worktree), logs it, tells the owner the new thread id, and stops. LAND asked the owner first for the first handoffs only.
- **D4. The demo** runs the coordinator itself as a real T3 thread in a throwaway scratch project (`t3 project add`, then `t3 project remove` after). The owner sees two short-lived threads in T3.

## Review Focus

1. A slug that is not `^[a-z0-9][a-z0-9-]*$` (a URL, a path, empty): the skill stops and asks for the slug. It does not make a folder. (Task 2, SKILL.md step 1; Task 3 check 5.)
2. `HANDOFF-coordinator.md` with several blocks: the newest block is the **first** `# Coordinator handoff` heading in the file, not the last. The new coordinator takes its number from that block's `-> Coordinator N`. (Task 3 check 4 uses two blocks with the newer one first.)
3. No `rules-card.md` in the event folder: the brief has no rules-card line and no dangling link. With one: every brief has its absolute path. (Task 3 checks 2 and 3.)
4. `/hack-check` or `/hack-submit` not installed: the skill logs "not installed, skipped" in `COORD.md` at the step where it would run them, and goes on. (Task 2, SKILL.md step 9; Task 4 grep.)
5. A thread status file written while the page or the coordinator reads it: the brief tells threads to write a temp file in the same folder and `mv` it, as LAND's README says, so no reader sees half a file. (Task 1 brief template; Task 3 check 2 validates the JSON.)

  - Report to the coordinator `{coordinator_id}` with `{t3} thread send {coordinator_id} "<one line>"` when you finish, block or need the owner.
  - Before you report done, run a separate reviewer subagent on your diff and fix what it finds. Never merge your own PR: the coordinator merges after its own reviewer.
  - Anything new (a feature or a UI change not in this brief) needs the owner's OK: write it as a proposal, tell the coordinator, do not build it. Real bug fixes are fine as small PRs.
  - Hand off to a fresh session when your context nears about 140k: write what is done, what runs, and what is next in `{event_dir}/briefs/{name}-handoff.md`, then tell the coordinator.
  - Outside sites are read-only: never post, comment, message or submit on Devpost, Discord or GitHub web.
  - Never force push. Never rewrite main. Kill only processes you started, by PID.
  - Wording: plain short sentences. Never a middle dot as a separator.

  The event section has one labeled line per D2 slot: `Repo: {repo}`, `Base branch: {base}`, `Teammates: {teammates}`, `Ports never to use: {ports}`, `Wording: {wording}`, `Council judges: {judges}`, `Merge rule: {merge_rule}`, `Tests: {tests}`.

- [ ] **Step 2: Write `council.md`.** Header with the council name and status name; `{rules_card_line}`; `## Question` (what is decided); `## Inputs (read only)`; `## Goals the judges score against`; `## Method`: judges from the event rules; each round, fresh judges get the current draft and the goals (not your opinion) and score 1 to 10 with a critique; you revise and score again; stop when the average stops rising or every judge gives 9 or more; log every round's scores. `## Output`: `{event_dir}/councils/{name}.md`, ranked changes with round scores; report the path. Then `{rules_block}`.

- [ ] **Step 3: Write `fresh-eyes.md`.** Header with main's SHA; `{rules_card_line}`; `## Areas` (one separate reviewer subagent per area, in parallel; the coordinator lists the areas); `## Look for`: real bugs with a concrete failing input, README and docs claims the code does not back, breaks of the event's wording rules; `## Rehearsal`: run the demo path end to end on spare ports from a worktree of main and record the raw results; `## Fixes`: each real bug gets its own small branch and PR (test first), then tell the coordinator the PR number and head SHA; new features are proposals only. `## Output`: `{event_dir}/fresh-eyes-report.md`. Then `{rules_block}`.

- [ ] **Step 4: Write `reviewer.md`.** For one PR: `PR #{pr}, head {sha}, base {base}`. Read `gh pr diff {pr}` and check `git merge-tree` against the current base. Run `{tests}` in a scratch worktree, never in the main checkout. Check: does the change do what its issue says, are there real bugs (give the failing input), does it break the event rules or the generic rules, does the commit message follow the merge rule's trailer rule, is anything new beyond scope. Verdict on the last line: `MERGE` or `FIX: <numbered findings>`. Read only: no push, no merge, no comment anywhere. Kill only processes you started, by PID. Never use the event's listed ports.
